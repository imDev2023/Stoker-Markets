# Traps: the backend suite

Read before writing or debugging a file in `tests/backend`: the files share one stack and run in any order.
Moved out of `CLAUDE.md` on 2026-11-12 so it is read on demand; `CLAUDE.md` keeps the index.
The text is the original's, one sentence a line.

## The shared stack

- Backend test files share one stack and run in an order that changes between runs, so a test that adds up the operations wallet's SOL or the Ledger must allow for what any other file leaves behind: a SOL pot of a Quote Asset payout (`rewardPots()` in `fee-collector.test.ts`) and `reward_sale` entries, which are never revenue.
  Name revenue kinds positively (`platform_fee`, `pool_fee`, `fee_key`), never by excluding the others; `GET /v1/revenue` does the same for its days.
- The Fee Collector's cron (`15 * * * *`) runs two jobs, so a test that asserts the operations wallet's balance or a sweep's amount after it must allow for the Creator Forward: the sweep leaves the Creators' share behind and the forward then pays it (`forwarded()` and `pendingForCreators()` in `fee-collector.test.ts`).
  The manual endpoints `POST /v1/operator/jobs/fee-collector` and `/creator-forward` run one each.
- `budget-table.test.ts` changes the shared stack's Budget Table for good (a version that gives `rebates` a tenth out of the treasury's share, then one that takes it back), so on any later file the rebates' row holds an allotment nobody spends: a backend test that needs what the sweep leaves behind sums `availableLamports` over every row of `GET /v1/budgets`, never the Burn's and the Flywheel's alone, and no test may move the `burn` or `flywheel` share, since `burn.test.ts` asserts them as shares of the whole net.
  A version's start is judged by the wall clock and a Ledger entry's period by its block time, so a test waits until both have passed the start (`inForce` in that file) before it collects.
- An Active Day of the Creator Ladder lasts ten seconds on the backend stack (`activeDaySeconds` in `tests/backend/src/harness.ts`; a UTC day on the UI stack and everywhere else, and mainnet refuses `ACTIVE_DAY_SECONDS`), so a coin whose pool trades at least 1% of its Graduation Target in fifteen separate ten-second windows climbs to the second tier and its pool fee share stops being half: no file does that today, and a test that trades one pool for minutes must allow for it.
  `creator-ladder.test.ts` announces a quick ladder (two and three Active Days at the whole Graduation Target a day, so no other file's coin qualifies) and announces the first ladder's rule again before it ends, in `afterAll` if it failed, so the ladder's version number grows by two a run and no test may assert it.
  A coin's `activeDays` and tier move only when the Fee Collector runs, never by indexing a trade (`graduation.test.ts` compares a Creator's earnings before and after indexing alone).
  The count's day expression carries the day's length as text, not as a parameter: selected and grouped by with two parameters, Postgres takes them for two expressions and refuses the query.
- Creator Earnings Destinations (ADR 0011, 2026-11-10): a rule runs for every coin on the stack whenever any backend file runs the Creator Forward, and a buyback or a dividend moves the operations wallet's SOL, which `fee-collector.test.ts` asserts exactly, so `earnings-burn`, `earnings-holders` and `earnings-liquidity` each end by leaving their pots under the minimum (an `afterAll` collect and forward, the holders selling out, every locked position looked at); a new file that launches a coin with a rule must do the same, and a test reads its own coin out of the job's `rules` summary, never the run's status.
  LaunchLab's `buy_exact_out` delivers exactly `amount_out` to the wallet's spendable balance even for a Reward Launch (the tax is paid on top and sits withheld in the receiving account), but asked for more coins than the curve has left it delivers what is left and moves the curve to graduating instead of failing, and its `TradeEvent` reports the curve's payout before the coin's tax and the amount in without the Quote Asset's transfer fee.
  A liquidity addition is one transaction of up to 1,226 bytes (a Reward Launch's first, paired with SOL) and only fits through the Platform Lookup Table with the CPMM and lock authorities and the pools' CPMM config in it; the local chain's table has them from bootstrap, and on a table without them the rule extends the table itself and adds on a later run (`lookupTableWaits`, waiting 64 slots after any extension), which `earnings-liquidity.test.ts` proves with a second API on a table of its own.
  A `fee_key` job transaction's `subject` is the Fee Key's NFT mint since a pool can have many, the Fee Collector looks at 25 positions a run (`positionsLeftForLater` in its summary, so a test that needs every position collected loops until it is 0), and the wallet's collected tax is read from its associated account by address, never "the account the operations wallet owns", since the liquidity rule keeps a coin account of its own for each coin.
  Never edit `packages/*` while a backend run is in progress, a comment included: the API reloads.
  Two faults only the UI suite's seed met, both fixed in #193: a locked position whose fees are worth less than one unit of either token makes the pool refuse the collection with `ZeroTradingTokens` (CPMM 6006), which `simulateFeeKeyCollection` now reads as nothing to collect yet, so a tiny second addition on a stack with a tiny minimum no longer fails every Fee Collector run after it; and a buyback is a trade by the operations wallet, which the board's holder count (`queryLaunches`) and the Bundle Radar (`routes/trust.ts`) now leave out, or a coin with one real holder reads two and, inside the UI stack's 100,000-slot Snipe Window, two snipers.
- A Holding Day of the Holding Weight (ADR 0022) lasts ten seconds on the backend stack (`holdingDaySeconds` in `tests/backend/src/harness.ts`; a UTC day on the UI stack and everywhere else, and mainnet refuses `HOLDING_DAY_SECONDS`), so every Reward Engine run on the stack checks the coins that can have a round again, 25 a run, and a test that waits for its own coin's check loops on the summary's `holdingChecks` (`nextCheck` in `holding-weight.test.ts`: the coin may wait a run, and a run with `leftForLater` 0 that did not check it found it checked for its day already).
  The checks change no payout while the rules in force have no steps, and every other file works its payouts out pro rata by hand, so no file may ever leave a rules version with `holdingWeights` in force or announced: `holding-weight.test.ts` announces one, waits the stack's 60-second lead time (`REWARD_RULES_LEAD_SECONDS`, which the API never takes as less), and ends on a plain version again, in `afterAll` if a test failed.
  The rules version's number therefore grows by two a run and no test may assert it (`reward-rounds.test.ts` asserted version 1 until 2026-11-12), and every announcement must name `holdingWeights`, the empty list included, or it is refused with 400.
  A round's summary carries `weightedTotal` and a payout `weightedHolding`, so an exact `toEqual` on either names them (`earnings-holders.test.ts`).
  A check's time is its engine run's start, a lot's `since` is its check's time, and a round counts ages at its `startedAt`, so a test recomputes a Weighted Holding from the lots endpoint and the round's page alone; a snapshot the test must see without a check before it is an earnings round, which the Creator Forward opens and the engine never does.
- A Reward Launch with a Quote Asset payout and tax still to sell sells a slice and pays a round on every Reward Engine run, to whoever holds it (the treasury counts once it holds swept coins), and each sale on a curve leaves a Platform Fee in its Quote Asset's vault that may be too small to claim: a test that caps a run's payouts or expects an empty vault must allow for both (`reward-rounds.test.ts` "resumes", `fee-collector.test.ts` `dust`).
- The Burn's two-step buy leaves the surplus Quote Asset of its swap in the operations wallet (outside the Ledger), so `fee-collector.test.ts` subtracts `surplusOf(USDC)` before asserting the wallet's balance; a test that assumes the wallet holds only what Creators are owed fails whenever `burn.test.ts` ran first.

## What a test must set up

- The Snipe Window is 40 slots on the backend stack (`startStack`'s `snipeWindowSlots`; a buy inside it, then one after a wait of about 16 s, `trust.test.ts`) and 100,000 on the UI stack (`global-setup.ts`), so every seeded trade is a snipe and the coin baselines never depend on how long the seed took; the card prints whatever window the API reports ("the launch's first 100,000 slots (about 11 hours)" in the shots).
  Three buys sent at once on a fresh curve fail two of them with 6004 at the default 1% slippage, since each was quoted before the others landed: make a test's snipes one after another.
- Copy Protection refuses a second coin with a launched coin's name, ticker or image for the test stack's 45-second window, so the backend client's `prepare` gives every launch a name and ticker of its own (`uniqueTag`) and the UI suite's `launchViaApi` and `fillForm` a picture of its own (`coinImage(symbol)`); a test that launches two coins with the same explicit ticker from different wallets within 45 seconds sees the second refused with 409. A PNG with fewer than 6 hash bits (flat, or one straight edge) is never compared, so a test that wants an image copy caught uses stripes.
  A visual shot of a filled launch form waits for the copy check's verdicts first (`copyCheckSettled`), or it catches "Checking".
- An airdrop at launch is only for Creator wallets the operator has allowed (`/v1/operator/airdrop-creators`, one `platform_settings` row; empty by default, so the form shows no airdrop and `prepare` answers 403).
  Tests allow a wallet first: `allowAirdrops` in both suites' helpers, and the backend `prepare` helper does it unless `unlisted` is set.
- The Reward Engine's job summary (`POST /v1/operator/jobs/reward-rounds`) covers every Reward Launch there is: a test reads its own coin's entries by mint, and runs the engine once first when it wants a run's `sold` or `paid` to be its coin's alone.
  A Quote Asset payout's sale is bounded by the market as it stands at that run, so compute the cap (`loadCurve`, 0.5% of `virtualBase - realBase`) right before the run that sells.
