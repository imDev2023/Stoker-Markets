# Traps: stacks, worktrees and the Mac

Read before starting a dev stack, running a suite from a worktree, or reading a run that failed with timeouts or HTTP 500.
Moved out of `CLAUDE.md` on 2026-11-12 so it is read on demand; `CLAUDE.md` keeps the index.
The text is the original's, one sentence a line.

- A worktree whose branch has a contract or migration change the dev stack's branch lacks cannot read the 8791 API (zod rejects the old shape on every page).
  Give it its own API and database, never migrate the dev database under the owner's stack: `docker exec launchpad-postgres psql -U launchpad -c 'CREATE DATABASE <name>'`, migrate it with `runMigrations` from `tools/stack` (`pnpm exec tsx -e 'import("@launchpad/db/migrate").then(m => m.runMigrations("<url>"))'`), copy the main checkout's `apps/api/.dev.vars` into the worktree, then from its `apps/api` run `WRANGLER_HYPERDRIVE_LOCAL_CONNECTION_STRING_HYPERDRIVE=<url> pnpm exec wrangler dev --port 8793 --inspector-port 9231 --test-scheduled` with the `--var`s from `state.json` plus `PUBLIC_API_URL` and `WEB_ORIGIN` for 8793 and 3101, one `GET /__scheduled`, and the web with `NEXT_PUBLIC_API_URL=http://localhost:8793 pnpm exec next dev --port 3101`; the chain and the Arweave stand-in are shared (2026-10-10).
  Port 8792 belongs to another session's wrangler.
- A dev stack run from a worktree (2026-10-30): the chain on 8899 belongs to whichever worktree started it, so use that worktree's `state.json` and `.dev.vars` (its `OPERATIONS_KEY` matches its chain; the main checkout's did not); never pass `PRICE_SOURCE=static` to a dev API on the mainnet quote set (one asset launchable); the UI suite's seed assumes the test stack's 1 SOL `GRADUATION_TARGET_LAMPORTS`; `wrangler dev` through `pnpm exec` is three processes and killing one makes the pnpm parent respawn the others on the port, so kill all three and check `lsof` before restarting; in zsh `kill $pids` fails on a trailing space (`${=pids}`); a failing visual project skips the flows (Playwright dependencies), so a flow's failure can surface only on the second run; `pnpm test:ui` leaves `apps/web/.next-test-<port>` folders behind; orderings that break ties by signature flip between runs (order by `createdAt` or `recorded_at`); a young seeded coin's shot flips across the 45-second Copy Protection window unless it waits for "ended" (`copyWindowEnded`); the `/` shortcut test must blur the board's autofocused search first.
- A stack started from a worktree reads that worktree's `tools/localnet/.keys`, shared by every stack and script run from it: replacing those files under a running suite swaps the admin, migrate and mint-authority keys under the tests (the dev chain's keys copied in for a seed script failed 12 backend tests, 2026-10-29); a seed that needs `mintLocalQuote` runs before the suite, or from the chain's own worktree.
  Each stack's ledger is its own (`.ledger/<rpc port>`), so two suites from one worktree can run side by side.
- A long CPU job on the Mac (the key grind) starves the local chain: the backend suite then fails with timeouts in unrelated files.
  Another session's video render does the same and cannot be paused from here (the marketing folder's `render.mjs`, ffmpeg on every core, load average 150 on 2026-11-09): the backend suite took 20 minutes instead of 8, a wait counted in seconds fell short of its slots (`marks.test.ts`, which now counts slots), and one coin page never reached `networkidle` in a UI run, which skips every flow after it; read `uptime` before reading such a failure, and run again once the load has gone.
  Pause it (`kill -STOP <pid>`) for a run and resume it (`kill -CONT`); when the run is a background chain that gets stopped, the resume never runs, so check `ps -o stat= -p <pid>` (`T` is still paused) after any run.
  In zsh `status` is a read-only alias of `$?`, so `status=$?` after the run aborts the script before the resume (2026-10-07): name it `rc`, and put the resume in `trap '...' EXIT`.
- A backend run where most files fail with HTTP 500 means Docker went down under it (it does not come back by itself after a restart of the Mac: `open -a Docker`), not a regression.
  When Docker stops answering altogether (2026-11-06: `docker ps` hung for over half an hour after another project's render drove the load average to 459, and a UI run's flows failed with `fetch failed`), the Mac's own PostgreSQL 18 runs a private server from a scratch folder (`/Library/PostgreSQL/18/bin/initdb -D <dir> -U test --auth=trust`, then `postgres -D <dir> -p <free port> -c listen_addresses=127.0.0.1 -c unix_socket_directories=` in the background, since a socket path under the scratchpad is too long) and `STACK_DATABASE_URL=postgres://test:test@127.0.0.1:<port>/postgres` runs either suite on it without touching Docker.
